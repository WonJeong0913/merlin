## 5. P0 — provider-rollout corroboration

`merlin/src/merlin_harness/provider_rollout_evidence.py`, and
`docs/provider-rollout-corroboration-v1.md`.

Every hash in a `skill_body_invocation` event is computed by the harness about
the harness; a lying harness would emit a valid signature. The Codex CLI writes
a rollout per session under `~/.codex/sessions`, **including `source: "exec"`
sessions (40 of 192 on this machine)**, `session_meta.id` equals the exec

- `locate_rollout` fails on ambiguity rather than guessing;
- the skill body is re-read and re-hashed; a body that drifted since signing is

  the request does not appear in the serialized record.

Validated against a **real** rollout on disk (`source: exec`,
`cli_version 0.108.0-alpha.12`, 6,243-char request): positive match and a
negative control both behaved.

**The gate did not move.** Tier availability is a mechanism, not a corroborated
observation; a test asserts an available tier does not flip
`provider_native_evidence_complete`. Roadmap P0 stays unchecked, marked
"mechanism built, unexercised".

## 6. HarnessX audit

Audited against the Codex binary's own embedded hook schema, not from memory.

**Sound**: per-hook mutation allowlists enforced by deep-copy field diff; rollback
target pinned to the exact parent before promotion; seesaw treats a *missing*
outcome as failure; cumulative same-dimension drift escalates to approval; the
approval policy is caller-supplied and **not** readable from the variant, so a
candidate cannot loosen its own bar. Adapter output matches Codex's
`additionalProperties: false` schema, and fail-closed is real — Codex's own error
string is *"PreToolUse hook exited with code 2 but did not write a blocking
reason to stderr"*, and the adapter does both.

**A correction I made mid-audit**: I reproduced an `IndexError` on a
zero-processor policy and nearly filed it as a defect. `load_live_tool_policy`
already requires exactly one registered policy processor, and both admitted
processors are pinned to `before_tool`, so it is unreachable through the CLI. My
reproduction bypassed the loader.

**A real hole, found by probing**: a change manifest that `REMOVE`s the only
guard processor passes **all seven gate checks** with `requires_approval=False`.
Three causes compound — `seesaw` measures task outcomes only and removing a deny
guard allows *more*; `risk_tier` is self-declared by the manifest; and
`_validate_variant` accepts an empty processor set. The verifier that should have
caught it crashed with `IndexError` instead of reporting the deny failures.

- **fixed**: the crash. A guard-removed variant now reports all three deny cases
  as failed → `smoke_passed=False` → gate rejects with
  `candidate_rejected_rollback_parent`;
- **not fixed**: the gate itself still accepts guard removal when a caller
  supplies `smoke_passed=True`. That is a design decision about the gate, so it
  is recorded as a documented known-gap test rather than silently changed.

Blast radius: `load_live_tool_policy` refuses a zero-processor policy, so the
realistic outcome is a broken gate, not a silently ungoverned one.

**Also**: the live hook is **not registered**. No `[hooks]` in
`~/.codex/config.toml`, no `~/.codex/hooks.json`. Codex 0.146 supports hooks
(10 events, `trusted_hash` required) but the gate is code only. And 2 of 8 typed
hooks are externally bridged; `SessionStart`/`SessionEnd`/`UserPromptSubmit` map
naturally to `task_start`/`task_end`/`before_model` and are unwired.

`experiments/mvp/measure_deterministic_selection.py`,

**Primary — mechanical queries (`task_id` with hyphens as spaces), n = 87:**

| k | recall@k | precision@k |

**Three things I got wrong first and corrected:**

2. Queries were mine in both arms. The primary arm is now mechanical, with no
   human judgement in it.
3. I called a 5/6→1/6 contrast a collapse. **Exact two-sided sign test gives
   p = 0.125** — not significant, and with n=6 it cannot be. Demoted to an
   underpowered probe.

**Ceiling facts found**: all 209 skills have `trigger == description`, and
`governed_provisioning` scores `max(trigger, description)` — two evidence
channels carrying one signal. `validate_aip_lite_skill` passes 209/209 because
the adapter fills every field the gate checks; 8 skills pass `has_steps` on a

conveyance can be audited. That is safe only because these derive from public
