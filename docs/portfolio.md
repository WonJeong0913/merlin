# Merlin — 연구·개발 포트폴리오

기준일: 2026-09-07. 이 문서는 개인 연구 프로젝트의 설계, 구현 경험과
현재 검증 범위를 설명합니다. 완성된 상용 제품이나 성능 우위가 입증된
시스템으로 소개하지 않습니다.

## 한 문장 소개

**Merlin은 실행 경험을 바탕으로 스킬을 생성·선택·보수하고, 계약과 검증
결과에 따라 스킬의 생명주기를 관리하는 자기관리형 에이전트 하네스입니다.**

## 해결하려는 문제

스킬 파일이 많아지거나 과거 경험을 보유한다고 해서 태스크 성능이 자동으로
좋아지지는 않습니다. 어떤 스킬을 함께 사용할지, 보수 후 필요한 기능이
유지되는지, 실패가 실제로 다음 보수에 전달되는지를 실행 경로에서 확인해야
합니다. Merlin은 이 관리 문제를 연구합니다.

주요 연구 가설은 외부 관리 계층의 개선이 동일 모델의 실제 수행 능력을
높일 수 있다는 것입니다. 현재 가설을 검증하는 중이며, 정답이나 평가기를
바꿔 점수를 높이는 접근은 사용하지 않습니다.

## 프로젝트에서 다루는 핵심 설계

| 설계 요소 | 역할 | 현재 구분해야 할 점 |
| --- | --- | --- |
| G 유래 초기 스킬 집합 | 생성 실험의 87개 스킬에서 출발하고 Merlin의 보수 버전을 계승 | 초기 라이브러리에 C1 공식 스킬을 혼합하는 현재 실험이 아님 |
| AEGIS | 진단 → 계획 → 후보 보수 → 검토 | 실제 호출·산출 기록과 보수 효과는 별도로 평가 |
| HSEG | 스킬 계약과 의존·호환·중복·대안 관계를 고려하는 계획 구조 | 현재 경로의 선택/계약 연결은 관측; 모든 관계 연산의 효과가 입증된 것은 아님 |
| P/O/A/V/F 계약 | 보수 전후 요구와 실행 가능성을 연결하는 공개 계약 경계 | 선언·구조 검사 통과와 실제 기능 성공은 다름 |
| 격리와 승격 | 새 후보를 격리한 뒤 검증에 따라 사용·승격 여부 결정 | 코드/구조 테스트만으로 공식 성공 승격하지 않음 |
| 실행 증거 | 선택한 스킬 본문과 실제 요청 바이트, 검사·결과를 연결 | 본문 주입을 provider-native invocation으로 부르지 않음 |
| 경험 계승 | 허용된 이전 epoch 경험을 다음 진단·보수에 전달 | 같은 작업을 다시 푸는 적응과 처음 보는 작업으로의 전이를 구분 |

## 구현 과정에서 다룬 실제 문제

1. **선택되지 않으면 경험을 얻을 수 없는 초기 상태 문제**
   후보 탐색과 검증된 승격을 분리하는 방향으로 관리 경로를 개선했습니다.
   현재 실행에서 보수 후보의 격리 → 선택 → 요청 연결을 확인했습니다.

2. **보수·선택 코드가 있어도 실제 풀이에 연결되지 않는 문제**
   별도 테스트의 존재에 그치지 않고 실제 runner의 호출 경로, 스킬 본문
   해시·바이트 구간, 계약 결속과 hook 기록을 함께 확인합니다.

3. **공개 검사 관측이 수정으로 이어지지 않는 문제**
   완료된 실패와 시간 초과를 구분하면서, 관측된 시간 초과 진단에도
   남은 예산 안에서 한 번의 동일 세션 보수 기회를 제공하는 v67을 구현했습니다.
   세 작업 모두 실제 보수 턴을 받았지만 공식 점수 향상은 관측되지 않았습니다.
   v68에서는 공개 실패 진단을 보수와 다음 경험 전달에 더 구체적으로
   연결하는 통합과 집중 회귀 검증을 완료했습니다. 독립 재검증 후 같은 개발
   태스크 3개 실행을 완료했고, 공식 reward는 `0 / 0.16 / 0`입니다.

4. **실패 결과와 누락 결과가 섞이는 문제**
   유효한 공식 0점은 분모에 포함하고, 미채점·인프라 문제를 임의 0점이나
   성공으로 바꾸지 않습니다. 과거 결과와 새 버전의 결과도 합쳐 재라벨하지 않습니다.

## 맡은 역할과 개발 방식

프로젝트 소유자는 연구 방향·핵심 구조·실험 목표·수용 기준을 정의하고
개발과 실험을 조율했습니다. 구현 및 검토에는 AI 코딩 에이전트를 사용했으며,
현재는 총괄·구현·독립 검증 역할을 분리해 운영합니다.

포트폴리오에서 강조할 기여는 시스템 설계, 실험 운영, 실패 원인 분석,
실행 경로 통합과 증거 기반 검증입니다. 전체 코드를 수작업으로 단독 작성했다거나
독립적인 외부 연구기관이 검증했다고 표현하지 않습니다.

기술 범위: Python, Docker, BenchFlow/ACP 통합, typed runtime hooks,
상태·계약 모델링, JSON/SHA-256 증거 연결, 회귀 테스트와 실험 계측.

## 현재 결과를 어떻게 읽어야 하는가

최신 v68은 공식 검증 완료 **3/3**, reward **`0 / 0.16 / 0`**, 평균
**5.33점/100점**, 완전 통과 **0/3**입니다. v67 대비 평균 **+5.33%p**이나
v66과 같으므로 안정적인 성장이나 일반적 성능 우위를 입증한 결과는 아닙니다.
선택 본문 전달과 실패 경험 계승은 확인됐지만 공식 성공에 따른 승격은 **0건**입니다.

v66 개발 실험은 세 작업에서 공식 reward `0 / 0.16 / 0`이었습니다.
이후 완료된 v67은 **`0 / 0 / 0`**, 공식 검증 완료 **3/3**, 엄격한 통과와
양의 reward 모두 **0/3**입니다. 누락된 결과를 0으로 바꾼 것이 아닙니다.
평균 reward는 v66 대비 **5.33%p 하락**했고, 안정적인 성능 회복은 아직
달성하지 못했습니다.

v67에서 AEGIS 보수, HSEG 선택, 선택 본문의 정확한 요청 연결,
세 작업 각각 한 번의 동일 세션 보수와 공식 평가까지 실제로 관측했습니다.
이것은 실행 경로 통합의 증거이지 성능 향상의 증거가 아닙니다.
스킬 선택과 생성 결과도 달라졌으므로 하락 원인을 보수 턴 하나로 단정하지 않습니다.
이 세 작업은 반복 사용한 개발 세트이며, 전체 87개나 미관측 작업 성능을 대표하지 않습니다.

[연구 진행 현황과 한계](research-status.md)에 정확한 지표와 증거 범위를
공개합니다. 부진한 점수를 숨기지 않는 것도 실험 재현성과 연구 역량의 일부입니다.

## 다음 목표

- 보수 전후 공개 기능 검사 변화와 공식 성공을 함께 확인.
- 계약·경험 전달·보수·승격 경로가 실제 결과에 기여하는지 평가.
- 조건을 맞춘 C0/G 비교와 더 넓은 작업 집합에서의 성능 검증.
- 공개 가능한 코드·테스트·입력을 정리한 재현 패키지 제공.
- 그 이후 필요하면 library dilution / skill shadowing 가설을 별도 실험.

Shadowing 감소, 일반적인 자기진화 성능, C0/G 대비 확정적 우위는 현재
입증된 결과로 주장하지 않습니다.
