## 1. 수식·구현 정합성 검증

`implementation-start.md`의 수식 6종을 `src/the_king` 구현과 대조하고, 테스트·trace까지 실행 검증했다.

### 1.1 정합 확인된 것

| 수식 | 구현 | 판정 |
|---|---|---|
| SkillsBench `g = (p_skill − p_vanilla) / (1 − p_vanilla)` | `metrics.normalized_gain` | 일치 |
| More Skills `Δ(q,S) = p(q,S*(q)) − p(q,S)` | `metrics.library_induced_drop` | 일치 |
| `π_o = Pr(∅ ≠ I ⊆ S*(q))` | `metrics.clean_oracle_invocation_rate` | 일치 (분모 문제는 1.2-①) |
| `π_m` (최소 1개 distractor 호출 비율, paper-synthesis.md:107) | `metrics.shadowing_rate` | 일치 (동일 문제) |
| SkillRevise 선택 (첫 verifier-pass, 없으면 argmax U) | `metrics.select_first_success_or_best_utility` | 일치. Python `max`가 동률 시 앞 인덱스 반환 → argmin idx 정신과 일치. 단 호출자가 S_0을 첫 후보로 넣어야 함(docstring에 계약 미기재) |
| CTA `ΔP_τ = r⁺ − r⁻` | `cta_lite.compare_traces` `success_delta` | 일치. cost_ratio 0-나눗셈 가드 확인 |
| Self-Harness `accept iff Δ_in ≥ 0 ∧ Δ_ho ≥ 0 ∧ max > 0` | `metrics.self_harness_accept` | 로직 일치 (타입 문제는 1.2-②) |

### 1.2 발견·수정한 버그 4건

**① π_o/π_m 분모 오염 (실측 버그).**
oracle이 빈 task가 π_o를 희석하고 shadowing으로 잘못 집계됐다. 수치 재현: no-oracle task에서 스킬 선택 1건 + clean 1건 → `pi_o=0.5, shadow=0.5` (정답은 1.0, 0.0). `no_skill_when_oracle_rate`만 oracle≠∅ 조건이 있었고 나머지 둘은 없었다.
수정: 둘 다 oracle≠∅ 조건화, no-oracle task의 선택은 **`spurious_invocation_rate` 신설**로 분리. (`metrics.py`)

**② Self-Harness Δ 타입 오류.**
Δ는 pass-rate 차이(float)인데 `HarnessPolicyChange.delta_in/delta_held_out`과 `self_harness_accept` 시그니처가 int였다. 런타임엔 float도 동작하지만 스키마가 틀림 → float로 수정. (`models.py`, `metrics.py`)

**③ 포화 baseline에서 regression 은폐.**
`g(0.7, 1.0) = 0.0` — vanilla 포화 시 스킬이 성능을 깎아도 0 반환. 수정: 포화 시 raw delta(`p_skill − p_vanilla`) 반환 → regression이 음수로 보임. (`metrics.py`)

**④ Repair dead-end.**
`decide_candidate_lifecycle`이 REPAIR를 절대 반환하지 않았고, `apply_lifecycle_decision`은 REPAIR/MERGE/ADD_VALIDATOR를 조용히 무시(status 무변경)했다. 수정: regression 실패 → `LifecycleAction.REPAIR`(기존 HIDE — candidate는 active였던 적이 없으니 HIDE는 의미상 오류), `LifecycleStatus.REPAIR` 상태 추가, apply에서 처리. (`lifecycle.py`, `models.py`)

회귀 테스트 4개 추가 (`tests/test_core.py`): 분모 조건화, float Δ, 포화 regression, REPAIR 라우팅. 테스트 8 → 12개 통과.

### 1.3 기록만 한 것 (미수정)

- Δ = Δ_ctx + Δ_shd 분해 미구현 — oracle-only 조건 실행 필요, Phase 3+ 과제.
- CTA 라벨 임계값 1.5 하드코딩 — policy surface로 이동은 Phase 6.
- lexical_score의 장문 스킬 노출 편향 — provisioner 자체 편향으로 문서화 대상.

> **Figure 1.** The KING skill-harness management architecture. Four loops govern the skill lifecycle: (1) task execution with deterministic verification and trace logging, (2) trace-driven skill creation and SkillRevise-lite repair behind a validation/regression gate, (3) task-conditioned provisioning of active skills under an exposure budget, and (4) harness policy management driven by shadowing metrics (π_o, π_m, spurious invocation, no-skill fallback), where every policy update must pass a held-in ∧ held-out non-regression gate. ## 6. 첫 실측 결과

`experiments/mvp/results/library_scaling.json` (태스크 3, exposure budget 3, min_score 0.1):

```text
lib   pass  pi_o  pi_m  spurious  fallback  cost
  2   0.67  1.00  0.00   0.00     0.00      189
 12   0.67  1.00  0.00   1.00     0.00      363
 52   0.67  1.00  0.00   1.00     0.00      605
212   0.67  1.00  0.00   1.00     0.00      609
```

해석:

- **oracle-only(L2)는 완벽** — π_o=1.0, 오염 0.
- **라이브러리 12개부터 첫 오염**: control task(answer-yes)가 `sb/ac-branch-pi-model`(전력계통 스킬)을 spurious 호출. 1.2-①에서 신설한 spurious_invocation_rate가 첫 실측에서 바로 잡아냄.
- **shadowing(π_m) 미발생**: 태스크 3개뿐이라 oracle 스킬의 희귀 토큰(result/txt/summary)이 212개 라이브러리에서도 항상 승리. 부정 결과가 아니라 corpus 크기 한계 — Phase 1 확장이 전제.
- pass 0.67 고정: answer-yes는 결정적 executor가 스킬 없이 답을 못 만들므로 설계상 실패. exposure cost는 189→609로 3.2배 (context overhead 프록시 확보).
